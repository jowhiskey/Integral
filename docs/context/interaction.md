# Integral editor interaction spec (the binding contract)

**Status: COMPLETE — the owner interview closed 2026-11-07 (all 7 batches, S-001–S-110, ruled); this file is the BINDING CONTRACT for the DOM-layer behavior rework on `feature/editing-dom`. The rework scoping chat (2026-11-08) closed S-106 and added the Owner amendments section below.**

## What this is

The single source of truth for how live math editing in Integral must behave: every input × every caret position × every structure, as ruled by the owner. The oracle is the owner directly — the old prototype is not runnable anymore and is not the reference. The owner's knowledge base holds the authored original; this doc is the host-agnostic repo mirror for coding agents — identical rules, host-specific conventions removed.

Born from the 2026-11-07 model failure: the implemented interaction model was authored in chat scoping decisions without verification against owner intent and is FALSIFIED at the model level (swap-on-type, rejected-typing, bare empty slots everywhere, Ctrl+Backspace whole-node delete). **Until this contract rules otherwise, those past behavior rulings are VOID** — nothing may be built on them; the implemented engine/editor code still reflects them (the rework scoping sizes the changes against this contract). The mathjs oracle of the editing-engine arc verified parse agreement, never intent agreement. The visual-test catalog in `demo/` is the live-check surface; after the rework, its per-case expectations are regenerated from this contract.

## Rule table

Origin key: **ruled** (date, scenario ID) or **derived** (rule id) + spot-confirmed. Uncorrected predictions = confirmed (interview mechanic).

### Typing — Batch 1 (ruled 2026-11-07, S-001–S-020)

- **T1 — Rows are literal, text-like sequences.** A typed token appears at the caret; nothing restructures at edit time. Operators insert alongside (`a+b+|c` + `+` → `a+b++|c`, S-001), before an existing operator (`a|*b` + `−` → `a−|*b`, S-006), at row start (leading `+` allowed: `|a` + `+` → `+|a`, S-003 — "the user could type a → +a → 1+a"), at row end (S-005), from empty (lone `−`, S-004). Caret lands directly after the inserted token. `*` displays as × (S-002).
- **T2 — No in-place operator replacement** (standing question, ruled A): operator edits = delete + retype; typing behaves "as in any text editor". Select-then-type-over = deferred to a future selection-ranges feature (chat-side answer 2026-11-07).
- **T3 — Symbols and numbers are multi-character, text-like tokens.** A letter typed adjacent to a symbol glues onto the SAME symbol node, front or behind ("normal text input experience"; S-007 REVISED by the owner — supersedes the live-check "creates a new symbol" juxtaposition ruling; S-008 A). A token absorbs same-type input at any caret offset; different-type input SPLITS the token at the caret and inserts the matching node between the halves: `a|b` (one symbol) + `+` → `a+|b` (S-029), digit inside a symbol → the digit joins the SYMBOL NAME (S-030 A SUPERSEDED 2026-11-08 — digit-glue, see Owner amendments), letter inside a number → 5·x·3 (S-031 A), letter before a number → new juxtaposed symbol (S-032). **SPACE inserts a node boundary at the caret** (S-021, S-022): inside a token it splits it; at a token edge it separates the NEXT input from the current node, so same-type input starts a new node instead of gluing (type-mismatched input separates automatically — Space is only needed for same-type adjacency, e.g. two symbols in a row). Space leaves no visible mark. the owner's own take: valid but ambiguous UX, not recommended to users. Space-forced number-number adjacency: ruled FORBIDDEN (S-098 — Batch 7).
- **T4 — Numbers.** Digits extend at the caret (S-010). `.` joins a number as decimal point (S-011). A `.` that CREATES a new number node auto-prefixes zero — renders `0.`, everywhere a new number is born; caret INSIDE the new number, after the dot (`a|` + `.` → `a` juxtaposed with `0.|` — S-012 corrected by the owner, S-033 A). Second dot in a number: silently ignored (S-013) — **the rejection pattern: rejected keys are silent no-ops.**
- **T5 — Function names by paren conversion** (S-014 B; S-015): typed letters build an ordinary symbol (T3); `(` after a symbol whose name matches a known function converts it into the function token, opens the arg list, adds the closing fence immediately, caret inside. Autosuggestion box for partially typed names (functions/variables/symbols) = future feature, outside the base model. Non-matching names keep the S-017 A path (derived).
- **T6 — Parens never auto-wrap** (S-016; S-017 A): `(` creates a group with both fences at the caret; content to the left stays outside (implicit-multiplication reading).
- **T7 — Structure keys create 2D structures with □ placeholder slots** (S-018, S-019, S-020 — revises the live-check "invisible slots" ruling to a split): `^` → power with □ in the exponent; `/` → fraction whose numerator is the immediately preceding NODE (`a+b|` grabs `b`; `(a+b)|` grabs the whole group — the owner's example), denominator shows □ with the caret at slot start before it. **The split:** rows and row-level missing operands render bare (`−x+` stands); empty 2D structure slots render □ (U+25A1 — matches the shipped toMathML null-slot placeholder convention). **□ territory (Batch 2, ruled):** fraction denominator (S-019/S-026), power exponent (S-018), **function arguments** (S-023 A — the owner's reason: the backspace chain: deleting the last arg char → □ appears → next backspace deletes the entire function — anchor for the deletion batch), both slots of an empty fraction (S-025 A — caret in the numerator before its □). □ persists whenever its slot is empty, regardless of caret position (S-027 confirmed "exactly right with the right reason" — the standing affordance). **Group content: □ ruled (S-079 A, provisional — Batch 5):** an emptied group's content displays □ (the standing affordance, C2's click target); the owner unsure it is needed in this case — explicit option to change later. Deletion through it stays letter-wise (D8).
- **T8 — Dead keys (platform rule, S-018):** on dead-key layouts (German/Austrian QWERTZ: `^` is dead) the keypress gives no live feedback; the structure materializes with the NEXT typed character landing in the slot. Non-dead layouts: live on keypress with □. Dead ^ + SPACE → the power IS created with an empty □ exponent (S-035 B, ruled — "no reason to show the ^ character in a formula editor"; the OS-emitted literal ^ is swallowed as intent). Derived unified rule: after a dead ^ press, the next key press creates the power — a character lands in the exponent (S-034 pin confirmed), SPACE yields the empty □ state.
- **T9 — Keyless structures (root, subscript, units): ruled 2026-11-07 (S-028 discussion) — suggestion box (keyboard path) + palette (mouse path), backed by the SAME insertion vocabulary.** Old-prototype behavior confirmed as the box model: type a prefix (`sq`) → box offers matches (functions, structures, units, symbols) → select + Enter inserts; the typed letters stay an ordinary symbol until the conversion (consistent with T5's paren-conversion). REJECTED as entry keys: `/` and backslash ("too awkward", the owner). Box-mechanics mini-spec (key conflicts while open: ↑↓ navigate the box, Enter selects, Escape dismisses — formula caret nav suspended) = pinned when the box feature is designed; later-batch root/subscript/unit scenarios are drawn as already-inserted structures. Unit typing (`50|` + `mm` — unit node vs symbol) = Batch-3 card.
- **T10 — Function insertion is context-dependent (ruled 2026-11-07, Batch 5 / S-077 — amends T5 / S-014 B):** typing a function name + `(` always converts to the atomic head, but the auto closing paren is inserted ONLY when NO elements stand to the right of the caret (`sin(|□)`). With elements to the right, the head inserts bare over the existing content (`sin(|a+b`, no fence added) — a function never closes over content that was not in scope. S-014 B described the empty-right case only.

**Batch-1 supersessions recorded:** (a) live-check "letter in front of a symbol creates a new symbol" → T3 glue + Space-split; (b) live-check "empty operand slots are invisible, no □" → T7 split.

### Navigation — Batch 3 (ruled 2026-11-07, S-036–S-051)

- **N1 — Tokens step character-wise** (S-036 confirmed + the live-check number ruling): ←/→ move letter-by-letter inside symbols and digit-by-digit inside numbers, decimals included. All multi-char tokens are text-like.
- **N2 — One shared gap station (S-037 + chat 2026-11-07, ruled):** the position between two tokens is ONE station, not two (supersedes the old prototype's operator-attached/next-token two-station model). Backspace at the gap deletes the left token's last character (deletion UX); a typed letter glues into the right token (T3); typed digits/operators start a node at the gap. the owner chose the recommended single-gap model after surfacing the deletion-vs-gluing question himself.
- **N3 — Formula ends (S-038):** → at the very end / ← at the very start = silent no-op.
- **N4 — Horizontal arrows stay at the visual level (S-039 B, ruled — supersedes the prediction):** → at a slot's end EXITS the structure and lands after it in the row; the fraction's numerator end does NOT dive into the denominator (old prototype behavior, confirmed better UX by the owner). Confirmed exits: numerator (S-039 B), denominator (S-041), exponent (S-044), group content past the fence (S-046), last function argument (S-047).
- **N5 — Horizontal entry points:** → into a fraction from the left → numerator start (S-042); → at a power's base end → exponent offset 0 (S-043 note, ruled — the exponent is the next position to the right of the base). **Batch-7 pins (S-094–S-096):** ← into a fraction from the right → the NUMERATOR's end (S-094, ruled — NOT the geometrically adjacent denominator: the fraction's horizontal interface is the numerator on BOTH edges, matching S-042; the denominator is reachable only vertically or by click); ← at the denominator start → exits left past the whole fraction (S-095 confirmed — no horizontal left-neighbor inside); ← at the exponent's offset 0 → the base's end (S-096 confirmed, the S-043 mirror); ← from the right of a power → the exponent's end (S-094, confirmed).
- **N6 — Vertical arrows use caret memory (S-040, S-043, S-045, ruled — the owner references the vertical-memory feature; his V2 design from the DOM arc is the reference shape: per-region store, written on vertical exits incl. in-token index, read on vertical arrivals, stored-wins-if-it-resolves, nothing cleared):** ↑/↓ land at the target region's remembered position when one exists; otherwise at the END of the target slot. Memory serves vertical keys only (S-043 note). ↑/↓ on flat rows = silent no-op (S-048).
- **N7 — Function arguments read in order (S-047):** → at an argument's end steps past the comma into the next argument; at the last argument it exits past the closing fence.
- **N8 — Empty slots are normal slots for navigation (S-049):** → exits the structure; □ stays behind as the affordance.
- **Deletion-batch anchors from Batch 3:** (a) **Highlight-then-delete for structures (S-044 note, ruled):** Backspace at a station immediately AFTER a structure (`a^2|`) neither deletes the exponent nor the whole structure — it HIGHLIGHTS the entire structure red; the next Backspace deletes the whole structure. Presumed to apply to fractions/groups too — pin in the deletion batch. (b) **S-050 A → SUPERSEDED by S-098 (Batch 7):** Space still forces number-number adjacency as an editing state, but two adjacent number nodes without an operator are FORBIDDEN, not a tolerated ambiguity — "too dangerous to let it pass": **evaluation FAILS while the state persists.** Visual hint = a subtle seam/background marker between the two nodes (option B — visible but quieter than an error). (c) Backspace inside a symbol: unpinned at Batch 3 → ruled letter-wise in Batch 5 (D1/S-065 A).
- **Units typed after numbers (S-051 C, ruled):** vocabulary-dependent conversion — a letter run matching a known unit name converts into an attached unit (upright, tight spacing); unknown runs stay ordinary symbols. Same conversion shape as function names (T5); units also insertable via the suggestion box anytime. **Conversion fires ON LEAVING the letter run** (any non-letter key, arrow away, click away; longest match wins — `mm` → millimeter) — ruled 2026-11-07 chat. **Attached units are GRANULAR (S-104, Batch 7 — supersedes the old prototype's atomic-unit model and S-054's atomicity claim for units):** deletion/editing operates letter-wise inside a unit's letter run — `50mm|` + BS → `50m|` ("changing mm to m"); unit-ness re-fires per the S-051 rule on leaving the run: a still-known run stays an attached unit, an unknown run reverts to an ordinary symbol (derived). Mid-unit clicks resolve character-wise like symbols (C1, derived). Function heads remain atomic (C4/D7).

### Clicks — Batch 4 (ruled 2026-11-07, S-052–S-062)

- **C1 — Nearest-edge principle (S-052, S-053, S-058, S-060, the owner's corrections):** a click resolves to the nearest legal caret position: inside a slot, the nearest character edge of that slot's content (numbers and symbols character-wise, NOT always the end — S-058/S-060 corrections); operator glyphs map to the shared gaps flanking them (N2 corollary, S-053); past a slot's content → its end (S-055). Clicks never read or write the vertical-position memory (S-058, per the V2 design).
- **C2 — The □ is the empty slot's click target (S-057, confirmed):** clicking the □ (or its slot area) enters the slot, caret before the □. Closes the original live-check affordance question — the □ box IS the affordance.
- **C3 — The fraction bar maps to the flanking row gaps (S-056, ruled — none of the predicted options):** bar click → nearest SIDE of the whole fraction, 50/50 split: left half → the gap before the fraction, right half → the gap after it. The bar never enters num/den.
- **C4 — The function head is a unit (S-054 + chat 2026-11-07, RULED):** `sin(` including the open paren = the atomic function head; the closing paren is a MOVABLE token — deletable (yielding a legal-but-unbalanced, non-evaluable, error-annotated state) and insertable elsewhere. Clicking the head's name area → caret right after the open paren (first argument start); the head's left edge → the gap before the head. **Plain groups follow the SAME movable-closing-paren model (ruled same chat)** — parens are parens. Consequence: **highlight-then-delete is reserved for FENCELESS 2D structures** (power, fraction, root, subscript); paren-fenced containers (function, group) delete via the inward-consume chain: backspace works char-wise inward, an emptied region shows □, and backspace at the □ deletes the whole container (S-023). Ruled in Batch 5: BS at the gap before a function is the ORDINARY gap rule (D2 — deletes the left-adjacent token, never the function); the head deletes whole via D7 (BS at the argument start removes the entire head → the sin(→cos( swap workflow). **Typed-`)` pairing RULED (Batch 7, S-097):** a typed `)` completes the INNERMOST unclosed open fence to its left — a re-typed `)` restores the same function/group it belonged to; with nothing unclosed, it inserts as a literal dangling close paren, error-annotated (the movable model). Future feature note (the owner): a matched-pair HIGHLIGHTER like coding editors' bracket matching.
- **C5 — Background snap (S-061):** a click hitting no glyph snaps to the nearest legal position — past the end → formula end; empty formula → the single start position.
- **C6 — Double-click selects the clicked token (S-062 A, ruled):** text-editor behavior — the seed of the future selection-ranges feature. **Structure-level extension confirmed (Batch 7, S-099):** double-clicking a structure selects the WHOLE structure — token-click selects the token, structure-click selects the structure. Further selection details pin when the selection feature lands.

### Deletion — Batch 5 (ruled 2026-11-07, S-063–S-079)

- **D1 — Backspace/Delete in tokens: one character, letter-wise (S-063, S-069, S-065 A ruled):** BS deletes the character left of the caret; caret lands at the resulting offset. Inside symbols letter-wise, like a text editor — the owner: "we can afford letter-wise... VS Code also allows me to quickly insert variables with autosuggest but would never delete the whole variable on backspace." SUPERSEDES the falsified-era identifiers-atomic ruling. Converted tokens stay atomic (S-054) — BS at their boundary deletes the WHOLE token (function head; attached units are GRANULAR per S-104 instead). Forward Delete is the mirror: removes the character right of the caret, caret stays put; letter-wise in symbols likewise.
- **D2 — Backspace at gaps: consume the left-adjacent token (S-064, S-066 A ruled, S-077):** BS at the shared station (N2) deletes the left-adjacent token's LAST character — dangling operators included: `−x+|` → `−x|` (S-066 A; the implementation's no-op is a bug under the text model — "how would one even be able to delete the plus?"). An ATOMIC left-adjacent token goes whole (D1 corollary: function head, attached unit). BS at the gap BEFORE a function is the ordinary gap rule — it deletes whatever stands to the left (e.g. the `+`), never the function itself (S-077: the owner's correction of the predicted head-delete; the head deletes at the argument start instead, D7).
- **D3 — Ctrl+Backspace / Ctrl+Delete: split semantics (S-067 pinned, S-068, S-071 confirmed):** Ctrl+BS deletes everything left of the caret WITHIN the token; the whole token only at offset = length. Symbols identically (letter-wise per D1/S-065). Ctrl+Del is the forward mirror — everything right within the token; the whole right-adjacent token at a gap.
- **D4 — Empty formula: BS and Del are silent no-ops (S-078).** Same rejection pattern as N3.
- **D5 — Highlight-then-delete for fenceless 2D structures (S-072 confirmed; extends the S-044 power pattern per the Batch-4 chat ruling):** BS at a station immediately before/after a fraction, root, subscript, or power highlights the entire structure red; the next BS deletes the structure WITH its content. **Fires ONLY from OUTSIDE stations (S-109, Batch 7 — corrected the prediction):** with the caret INSIDE a structure's slot, BS is always char-wise (content → □) followed by the □-unwrap (D6) — at the exponent's end, the first BS deletes the `2` (□ appears), the second deletes the power and leaves the base standing. The highlight never triggers from inside.
- **D6 — BS at a □ unwraps and PROMOTES (S-073 — ruled to the owner's own third option; supersedes the falsified-era "structure dies iff ALL regions empty" rule):** BS at an empty slot inside a fenceless 2D structure deletes the structure and splices the SURVIVING sibling content inline at the structure's position, caret at the splice point: `x + frac(□,2)` → BS → `x + |2`. The power is the consistent case (S-074: `a^□` → BS → `a|`). Both slots empty → the structure dies outright, nothing promoted. **CONFIRMED (Batch 7, S-100–S-102):** the denominator-□ mirror (numerator promoted inline), root (radicand promoted) and subscript (dies, base stays), all at depth (S-109); and the asymmetry vs. D5 is INTENDED — deleting from OUTSIDE via highlight kills the content, deleting from INSIDE at the □ unwraps and keeps the surviving content (S-102: "remove this thing" vs. "unwrap it").
- **D7 — Function deletion: inward chain + head swap (S-075 confirmed — "the description is exactly right"; S-077 reopened-and-ruled):** (a) The chain stands: the movable closing paren deletes first (C4), then char-wise inward through the argument, the emptied argument shows □, BS at the □ deletes the ENTIRE function. (b) NEW: BS at the argument START (immediately after the head) deletes the entire atomic head `sin(` — content and closing paren survive: `sin(a+b)` → BS at arg start → `a+b)`; retype `cos(` → `cos(a+b)`. The function-swap workflow. the owner: the Batch-4 assumption that swapping functions required deleting the parens too was FALSE — surfaced by S-077. T10 is the matching insertion rule. The `sin(|□)` empty-arg chain (a) is explicitly unchanged.
- **D8 — Groups delete letter-wise through the content phase (S-076 RE-RULED — supersedes the Batch-4 chat assumption that groups mirror the function inward-consume chain):** "completely normal letter by letter deletion, including the opening parens": closing paren (movable, C4) → content char-wise. No highlight step, no special confirmation while content stands. The letter-wise reading originally extended to the opening paren at the empty point too — **REVISED by S-103 (Batch 7): at the fully-emptied □ the next BS deletes the WHOLE group** (see D9). The movable-paren model itself (C4) is untouched.
- **D9 — The emptied group shows □, and BS there deletes the WHOLE group (S-079 A + S-103 ruled, Batch 7 — closes the deferred S-024 and resolves the provisional interaction):** group content that empties displays the □ (the standing affordance and C2's click target). BS at `(|□)` deletes the entire group — both fences in one stroke (→ `|`) — NOT just the opening paren. The letter-wise chain (D8) governs the content phase; at the empty point the group behaves exactly like the function chain's empty-arg □ (whole-container death). The group and function deletion models CONVERGE at the empty point; they differ only in that a group's fences are plain characters while a function's head is atomic.

**Batch-5 supersessions recorded:** (a) falsified-era "identifiers atomic" → in-symbol BS letter-wise (S-065 A); (b) falsified-era "structure death iff ALL regions empty" → □-unwrap with promotion (S-073); (c) implementation's trailing-operator BS no-op → the operator deletes (S-066 A); (d) Batch-4 chat assumption "groups follow the function inward-consume chain" → groups letter-wise (S-076).

### Undo/Redo — Batch 6 (ruled 2026-11-07, S-080–S-088)

- **U1 — The undo unit: non-typing edits one per keystroke; typing runs COALESCE into deterministic bursts (S-080, S-081 B ruled, S-082, S-085, S-086).** A consecutive typing run is ONE unit, closed by any non-typing action (structure key, Backspace, arrow, click) — NO time threshold (the owner: "more predictable than with timing"; the timeout variant C explicitly rejected). Undo restores the pre-edit state including the caret position. Confirmed traces: the typo-fix chain walks unit-by-unit (S-082 — undo the retype, then the backspace, then the original run); the function-conversion chain (S-085, corrected by the owner — his sequence: `a+sin(a|)` → undo → `sin(|□)` → undo → the bare symbol `sin|` → undo → `a+|` — the `(`-press + conversion is ONE unit reverting to the symbol ALONE, no leftover empty group); the head-swap workflow (S-086 — undo removes the typed `cos(` head, the next undo restores the `sin(` head; the swap is two ordinary edits).
- **U2 — Structure creation/deletion are single units (S-083, S-084 A ruled).** One undo unwinds a structure creation including the node-grab (`b` back in the row, caret restored). The red highlight of highlight-then-delete is a TRANSIENT UI state, not an undo unit — the DELETE is the unit: one undo restores the whole structure with its content.
- **U3 — Redo mirrors undo (S-087).** Ctrl+Shift+Z / Ctrl+Y re-applies the last undone unit; any NEW edit clears the redo stack.
- **U4 — Empty undo/redo stacks: silent no-ops (S-088).**

### Special keys — Batch 6 (ruled 2026-11-07, S-089–S-093)

- **K1 — Home/End: local first, then ITERATIVE outward (S-089, S-090, S-091 ruled to the owner's iterative model — supersedes the predicted Ctrl+Home/End variants).** Home/End jump to the start/end of the current row/slot (inside a slot: the slot's own row — the N4 visual-level principle, never dives into a sibling slot). Pressed again when already at that boundary, they escalate one level outward — to the end/start of the enclosing row — iterating to the formula start/end ("pressing End multiple times gets you to the end of the formula eventually"). No Ctrl+Home/End variants. **RULED (Batch 7, S-105 A):** one level per press — escalating out of a slot goes DIRECTLY to the end/start of the enclosing row (not first to the position after the structure).
- **K2 — Enter and Tab commit and blur; the host takes over (S-092 ruled — supersedes the unbound prediction).** "Same as text input": Enter/Tab END the editing session (commit + blur), like a text input. The post-blur behavior (e.g. inserting a next row or advancing to the next cell in a host grid) is the HOST's convention, not Integral's.
- **K3 — Escape commits and blurs WITHOUT a follow-up action (S-093 ruled — supersedes the no-op prediction).** "Blurs the editor with changes persisting" — useful for evaluate-only, with no K2-style next-row/next-cell handoff. K2/K3 form a blur-commit family. **S-106 CLOSED (rework scoping chat, 2026-11-08): undo across blur is Integral-agnostic** — blur-commit ends the editing session and the undo history dies with it unless the host resumes it; the host decides resume vs. discard (the demo default is discard). The focused-granular vs. blurred-microversion question moves to the host integration, where the UX is testable.

## Owner amendments — rework scoping chat (2026-11-08; binding; supersede the cards noted)

Rulings from the rework scoping chat, after the interview closed.

- **Compatibility window:** old-reader/backwards compatibility does NOT bind — no user data exists, the editing state is wipeable, Integral is unpublished. Contract and AST changes are judged on design merit alone until the first external consumers (npm publish / beta); the additive-only discipline re-binds at that point.
- **Digit-glue — SUPERSEDES S-030 A's juxtaposition reading:** a digit typed directly after a symbol joins the SYMBOL NAME (`x` + `1` → `x1`). Digits are symbol-name characters wherever symbol letters exist to their left, including INSIDE a symbol (`a|b` + `5` → the ONE symbol `a5b`). Number nodes only form where no symbol precedes. Rationale: `x1`/`x2`-style indexing is the intent. (S-031/S-032 unchanged: letters before/inside numbers juxtapose/split; a digit typed before letters still starts a number.)
- **Juxtaposition evaluation (glyph-less adjacency):** a number before a symbol/group/structure (`5x`, `5(a+b)`) reads as implicit multiplication and EVALUATES — and, ruled 2026-11-08 in the rework session-1 digest chat, a GROUP before X (`(a+b)·x`) evaluates the same way (the session-1 code took the strictest (num, non-num) reading and refuses group-before-X; session 2a widens the projection predicate and re-pins the refusal tests; fn/unit-before-X stay refused unless ruled later); a symbol before anything REFUSES (`x` next to `3` is ambiguous with the name `x3`; `x(…)` is ambiguous with a function call) — evaluation error annotation, not a typing restriction; number next to number stays FORBIDDEN (S-098). Representation: glyph-less adjacency stores as a multiply row carrying an additive implicit marker (renders without the × glyph). The marker is a rendering/storability field only — never evaluation semantics.
- **Empty-slot operator rows — math-style projection (evaluation reading for op rows with null cells):** uniform with mathjs habits. A glyph whose LEFT cell is null applies unary to its right cell: leading `−` = negation, leading `+` = identity (`−x` rows evaluate); a doubled operator (one null cell between two glyphs, content after) acts on what follows — `2−−3` = 5, `a+b++c` = a+b+c. A glyph whose RIGHT cell is null (trailing null, `−x+`) leaves the expression incomplete → refusal; all-null rows and two consecutive null cells also refuse. Editor states only — the editor never creates unary nodes; the walker's own unaryMinus/unaryPlus nodes stay untouched (both representations render and evaluate identically). Lives in isEvaluable + the math-node projection.
- **Fence-state fields (C4/S-097 consequence):** the movable-paren model's fence fields (which close-fence belongs to which open fence, dangling closes) are rendering/storability concerns only. An unbalanced-fence state is storable and renders; evaluation refuses it through the EXISTING structural gate — no new evaluation rule.
- **S-106 CLOSED — undo across blur is Integral-agnostic:** blur-commit (K2/K3) ends the editing session, and the undo history dies with it unless the host resumes it; the host decides resume vs. discard. The demo page default = discard. The focused-vs-microversion question moves to the host integration (where the UX is testable); Integral needs no decision — rework session 5 implements blur-commit without history carry-over.

## The coverage matrix (the definition of "100% coverage")

A cell = (input, structure/state, caret position). A cell is COVERED when ruled by the owner, or derived from a ratified rule and spot-confirmed. The spec is complete when every cell is covered and the rule table below is closed.

- **Inputs:** ←/→/↑/↓; Backspace; Ctrl+Backspace; Delete (forward); Ctrl+Delete; digits 0–9; letters; `.`; operators `+ − * / ^`; parens; comma; undo/redo keys (+ granularity); click variants (glyph interior, glyph edges/outer zones, seams, container bodies — numerator/radicand/args —, background); Enter/Escape/Home/End (ruled Batch 6 → K1–K3: iterative Home/End; Enter/Tab/Escape = the blur-commit family).
- **Structures/states:** empty formula; number (integer, decimal, negative); symbol; symbol juxtaposition; operator rows (single op, mixed ops, leading op, trailing op, double-op literal states like `a+b++c`); fraction in every fill state (incl. both-empty); power; root with/without index; parens group (empty, nested, unbalanced-during-typing); function (0/1/2 args, empty arg, comma, name typing); unit; subscript; nested combinations of the above; freshly-typed intermediate states.
- **Caret positions:** in-token offsets (incl. 0 and len); glyph boundary; row seams (start/interior/end); structure stations (num, den, exp, radicand, index, arg cells); invisible empty slots; end-of-row/end-of-everything.
